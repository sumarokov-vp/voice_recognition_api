## Маршрутизация (кто запускает выкат)

Выкат инкапсулирован в самодостаточном `deploy-prod.py` — по сложности, а не по умолчанию:

- **Зелёный однокомандный выкат** (просто выкатить свежий код — скрипт делает всё сам):
  запускай **напрямую из главного диалога**, не делегируя. Это одна готовая команда,
  агент-обёртка тут лишний.
- **Делегируй агенту `devops`** только когда выкат перестаёт быть однокомандным и нужна
  инфра-логика: разбор упавшего контейнера на месте, ручные операции на сервере, правка
  серверного `.env`, работа с сетью и туннелем. Тогда передай агенту процедуру ниже.
- **Если ты уже агент `devops`**: выполняй процедуру напрямую. НЕ спавни другого devops и НЕ
  вызывай этот скилл повторно — иначе рекурсия.

## Процедура

Точка входа — `deploy-prod.py`. Запуск **только через `uv run <script>`** (script-mode:
поднимает inline-зависимости PEP 723; `uv run python …` их игнорирует — так не запускать):

> Обычный выкат:
> `uv run .claude/skills/deploy/scripts/deploy-prod.py`
>
> План без обращения к серверу:
> `uv run .claude/skills/deploy/scripts/deploy-prod.py --dry-run`

Сообщи пользователю результат — успех с ответом `/health` или ошибку из вывода скрипта.

## Что происходит на сервере

Рабочей копии на сервере нет: разработка живёт на маке, сервис — на домашней рабочей
станции. Поэтому серверный `compose.yaml` намеренно без блока `build`, а собирает выкат:

1. `rsync` исходников (`Dockerfile`, `.dockerignore`, `pyproject.toml`, `uv.lock`,
   `README.md`, `src/`) и `docker-compose.yml` во временный каталог сборки.
2. **Префлайт**: серверный `.env` на месте, на сервере есть buildx, и доставленный
   compose разворачивается `docker compose config` с этим `.env`.
3. `docker build -t voice-recognition:latest .` — там же, с BuildKit.
4. Проверенный compose ложится в каталог сервиса, `docker compose up -d`.
5. Ожидание `healthy`, затем `curl -sf http://localhost:8000/health` **с самого сервера**:
   снаружи порт опубликован не для всех сетей, а localhost открыт всегда. Ответ должен
   содержать `loaded: true`.
6. Временный каталог сборки удаляется. После **упавшего** выката он остаётся — по нему
   разбирают, что именно уехало; путь и команда уборки печатаются.

Первым делом печатается шапка «что уезжает»: ветка, коммит, неотправленные коммиты и
состояние рабочей копии в выкатываемых путях. Уезжает рабочая копия как есть, а не коммит.

## Чего выкат не трогает

`.env` и `models/` в каталоге сервиса — ни при каких флагах. В `.env` лежат настройки
конкретной машины (модель, cuda, `HOST_UID`/`HOST_GID`), в `models/` — несколько гигабайт
весов, которые незачем возить.

## Красный префлайт — это не поломка

Префлайт стоит **до** сборки и до подмены живого compose. Когда он красный, на сервере
изменён только временный каталог: живой `compose.yaml` прежний, контейнер работает,
`.env` и `models/` нетронуты. Типичная причина — в серверном `.env` не хватает переменной,
которую compose репы объявил обязательной (`API_KEYS`). Чинить надо `.env` на сервере,
а не обходить префлайт флагом: такого флага нет намеренно.

## Доступ

Per-machine доступ к серверу — SSH-алиас в `.claude/config.local.yaml`
(`skills.deploy.prod_ssh_alias`; резолвер `.claude/lib/machine_config.py`; env-override
`$PROD_SSH_ALIAS`). Host, пользователь и приватный ключ — в `~/.ssh/config` под этим
алиасом; адресов, имён хостов и секретов в самом скилле нет.

Заход требует касания аппаратного ключа — это норма, а не зависший ssh: выкат запускает
человек. Касание одно на весь прогон, у алиаса включён `ControlMaster` с `ControlPersist`.
По той же причине скрипт не использует `ssh -o BatchMode=yes`.

Сервис доступен ровно тогда, когда рабочая станция включена: резерва и SLA нет.
При ошибке выката не править вручную на сервере — исправить локально (скрипт, compose,
код) и запустить выкат заново.
