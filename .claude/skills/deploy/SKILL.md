Выкат voice_recognition. $ARGUMENTS

## Две цели, обе боевые

Сервис работает **в двух местах одновременно**, и это надолго. Mac mini не заменяет домашний
сервер: потребители переводятся по одному, домашний никто не гасит. Пока перевод не закончен,
свежий код нужен обеим машинам.

Цель    | Машина                | Движок и железо                    | Как живёт                     | Команда
--------|-----------------------|------------------------------------|-------------------------------|------------------------------
`home`  | домашний Linux-сервер | `faster-whisper`, NVIDIA CUDA      | контейнер docker              | `deploy-prod.py` (по умолчанию)
`mini`  | Mac mini              | `mlx-whisper`, Apple Metal         | нативный процесс под launchd  | `deploy-prod.py --target mini`

Цель по умолчанию — `home`: прежняя однокомандная выкатка работает ровно как работала, флаг
для неё не нужен.

## Процедура

Точка входа — `deploy-prod.py`. Запуск **только через `uv run <script>`** (script-mode:
поднимает inline-зависимости PEP 723; `uv run python …` их игнорирует — так не запускать):

> Домашний сервер:
> `uv run .claude/skills/deploy/scripts/deploy-prod.py`
>
> Mac mini:
> `uv run .claude/skills/deploy/scripts/deploy-prod.py --target mini`
>
> План без обращения к машине (работает для обеих целей):
> `uv run .claude/skills/deploy/scripts/deploy-prod.py --target mini --dry-run`

Сообщи пользователю результат — успех с ответом `/health` или ошибку из вывода скрипта.
Выкатываешь обе машины — запусти команду дважды, целями по очереди.

## Маршрутизация (кто запускает выкат)

Выкат инкапсулирован в самодостаточном `deploy-prod.py` — по сложности, а не по умолчанию:

- **Зелёный однокомандный выкат** (просто выкатить свежий код на любую из целей — скрипт
  делает всё сам): запускай **напрямую из главного диалога**, не делегируя. Это одна готовая
  команда, агент-обёртка тут лишний.
- **Делегируй агенту `devops`** только когда выкат перестаёт быть однокомандным и нужна
  инфра-логика: разбор упавшего контейнера или демона на месте, ручные операции на машине,
  правка `.env`, пересборка `.venv`, работа с сетью и туннелем. Тогда передай агенту
  процедуру ниже.
- **Если ты уже агент `devops`**: выполняй процедуру напрямую. НЕ спавни другого devops и НЕ
  вызывай этот скилл повторно — иначе рекурсия.

## Что происходит на домашнем сервере (`home`)

Рабочей копии на сервере нет: разработка живёт на маке, сервис — на домашней рабочей станции.
Поэтому серверный `compose.yaml` намеренно без блока `build`, а собирает выкат:

1. `rsync` исходников (`Dockerfile`, `.dockerignore`, `pyproject.toml`, `uv.lock`,
   `README.md`, `src/`) и `docker-compose.yml` во временный каталог сборки.
2. **Префлайт**: серверный `.env` на месте, на сервере есть buildx, и доставленный
   compose разворачивается `docker compose config` с этим `.env`.
3. `docker build -t voice-recognition:latest .` — там же, с BuildKit.
4. Проверенный compose ложится в каталог сервиса, `docker compose up -d`.
5. Ожидание `healthy`, затем `curl -sf http://localhost:8000/health` **с самого сервера**:
   снаружи порт опубликован не для всех сетей, а localhost открыт всегда. Ответ должен
   содержать `loaded: true`.
6. Временный каталог сборки удаляется. После **упавшего** выката он остаётся — по нему
   разбирают, что именно уехало; путь и команда уборки печатаются.

## Что происходит на Mac mini (`mini`)

Здесь нет ни образа, ни compose: сервис — обычный процесс, запущенный launchd из рабочей
копии `~/projects/voice_recognition`.

1. **Префлайт** (идёт ПЕРВЫМ, до доставки исходников): на месте рабочая копия, `.env`,
   `.venv/bin/python`, демон `system/com.sumarokov.voice-recognition` загружен, `uv` находится.
   Тут же читается адрес проверки (`API_HOST`/`API_PORT` из `.env` на машине) и sudo-пароль
   из `pass`. Ничего из этого выкат не создаёт: `.venv` собирается руками, plist кладёт
   pyinfra, `.env` — собственность машины.
2. `rsync` исходников (`src/`, `pyproject.toml`, `uv.lock`, `README.md`) прямо в рабочую
   копию. `--delete` работает только внутри `src/`, чтобы удалённый в репе модуль исчез и
   там; `.env`, `.venv` и `.git` рядом не трогаются.
3. `uv pip install --python .venv/bin/python -e '.[server,mlx]'` — **доустановка**
   зависимостей в существующее окружение. Не `uv sync`: тот привёл бы `.venv` к локфайлу
   целиком и выкинул бы движок, поставленный под маркером платформы.
4. `sudo launchctl kickstart -k system/com.sumarokov.voice-recognition` — перезапуск демона.
   Пароль уезжает в stdin, не в аргументах. Следом сверяется pid демона до и после: процесс
   обязан смениться, иначе зелёный `/health` мог бы прийти от старого процесса.
5. Ожидание `/health` с `loaded: true` **с самой mini**, по адресу из `.env`
   (сейчас `http://10.70.0.8:8000/health`). Не дождались — печатаются последние строки
   `~/Library/Logs/voice-recognition.log`.

Порядок стадий обратный домашнему намеренно: там исходники уезжают во временный каталог
сборки и живого сервиса не касаются, здесь — ложатся прямо в рабочую копию, из которой сервис
запускается. Пускать их туда, не проверив машину, нечем оправдать.

Рабочая копия на mini после выката становится «грязной» относительно своего git — так и
задумано: туда уезжает рабочая копия с мака как есть, а не коммит.

## Почему на mini без docker

**Это ограничение платформы, а не предпочтение.** GPU на macOS не пробрасывается ни в одну
Linux-VM — ни у colima, ни у Apple `container`. Metal доступен только нативному процессу
macOS. В контейнере `large-v3` считал бы на CPU со скоростью около 1x реального времени;
нативно на MLX turbo-модель даёт 3.9x. Попытка «унифицировать» выкат на mini обратно в docker
отняла бы у сервиса GPU — делать этого нельзя.

**Почему LaunchDaemon, а не LaunchAgent или `brew services`.** Mac mini headless: графического
логина нет, домена `gui/<uid>` не существует, и `brew services` там падает с `Domain does not
support specified action`. Демон живёт в системном домене — отсюда и root на перезапуск.

## Чего выкат не трогает

Ни при каких флагах и ни на одной цели:

- `.env` на обеих машинах — там настройки конкретной машины (движок, модель, адрес, ключи,
  `HOST_UID`/`HOST_GID`).
- веса моделей: `models/` в каталоге сервиса на домашнем сервере, кеш `~/.cache/huggingface`
  на mini — гигабайты, которые незачем возить.
- на mini дополнительно: `.venv` целиком (выкат только доустанавливает в него зависимости) и
  plist демона — его раскладывает pyinfra, а не выкат.

## Красный префлайт — это не поломка

Префлайт на обеих целях стоит так, чтобы его провал оставлял живой сервис нетронутым: на
домашнем сервере изменён только временный каталог сборки, на mini — вообще ничего. Типичная
причина на `home` — в серверном `.env` не хватает переменной, которую compose репы объявил
обязательной (`API_KEYS`); на `mini` — нет `.venv` или не загружен демон. Чинить надо машину,
а не обходить префлайт флагом: такого флага нет намеренно.

Что осталось на машине после падения, скрипт печатает сам — отдельной подсказкой под ошибкой,
и на mini она зависит от стадии (исходники ещё не уезжали / уже лежат, но демон на старом коде
/ демон перезапущен).

## Доступ

Per-machine доступ — `.claude/config.local.yaml` (резолвер `.claude/lib/machine_config.py`,
шаблон — `.example`). Адресов, имён хостов и секретов в репозитории нет:

Ключ                          | Что это                                              | env-override
------------------------------|------------------------------------------------------|---------------------------
`skills.deploy.prod_ssh_alias` | SSH-алиас домашнего сервера                          | `$PROD_SSH_ALIAS`
`skills.deploy.mini_ssh_alias` | SSH-алиас Mac mini                                   | `$MINI_SSH_ALIAS`
`skills.deploy.mini_sudo_pass_entry` | **путь** к записи `pass` с sudo-паролем mini   | `$MINI_SUDO_PASS_ENTRY`

Host, пользователь и приватный ключ — в `~/.ssh/config` под алиасом. Sudo-пароль лежит в
`pass` и читается **на машине разработчика**: на самой mini нет ни pass, ни gpg. В `.env`
и в конфиг он не попадает никогда.

Заход на обе машины требует касания аппаратного ключа — это норма, а не зависший ssh: выкат
запускает человек. Касание одно на весь прогон, у алиасов включён `ControlMaster` с
`ControlPersist`. По той же причине скрипт не использует `ssh -o BatchMode=yes`.

Login shell на mini — fish, а команды выката написаны на POSIX sh, поэтому туда они уезжают
завёрнутыми в `bash -c`; на домашнем сервере login shell и так bash. В неинтерактивном bash на
mini нет `/opt/homebrew/bin` в `PATH` — команды, которым нужен `uv`, добавляют его сами.

Домашний сервис доступен ровно тогда, когда рабочая станция включена: резерва и SLA нет.
При ошибке выката не править вручную на машине — исправить локально (скрипт, compose, код) и
запустить выкат заново.

## Раскладка скриптов

Файл                      | Ответственность
--------------------------|--------------------------------------------------------------
`deploy-prod.py`          | точка входа: разбор аргументов, выбор цели, чтение конфига, обработка ошибок
`i_deploy_target.py`      | контракт цели — то, что нужно точке входа
`deploy_home_docker.py`   | цель `home`: сборка образа на сервере и перезапуск compose
`deploy_mini_native.py`   | цель `mini`: rsync, `uv pip install`, `launchctl kickstart`
`deploy_working_copy.py`  | шапка «что уезжает» (общая, пути даёт цель)
`deploy_health.py`        | опрос `/health` до `loaded: true` (общий критерий «доехало»)
`deploy_remote_shell.py`  | команды по ssh, в том числе с секретом в stdin
`deploy_console.py`       | печать, запуск локальных команд, `PreflightError`

Добавляется третья машина — появляется ещё один файл цели и ветка в `build_target`; общие
части (шапка, `/health`, ssh) трогать не придётся.
